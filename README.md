# Tradzen

Read-only browser extension (`extension/`) → local backend (`backend/`) → signals + dashboard. See `PLAN.md` for the full plan.

## Run it
1. **Backend** (PowerShell, in `backend/`):
   ```
   .\start.ps1
   ```
   Dashboard: http://127.0.0.1:8787/ (signals are stored in `backend/data/signals.db`).
2. **Extension**: `chrome://extensions` → reload *Tradzen Sniffer* (version must read **0.3.0**; it now needs the new "side panel" and localhost permissions → accept the prompt).
3. Open Quotex in a normal logged-in tab, hard-reload it (`Ctrl+Shift+R`), open a chart.
4. Extension icon → **Open signal panel** (or open the dashboard in a tab). The popup shows "Signal backend: connected".

Signals appear when a candle closes and the pair has ≥ 60 candles (history loads when you open the chart; otherwise it fills live).
Each signal is for the **next** candle and is settled automatically. Win accuracy on the dashboard is measured, not promised — judge it only after a few hundred settled signals and compare it with the break-even line.

## Alerts (extension 0.4.0)
When a BUY/SELL signal is issued, a card appears on the Quotex page (pair, direction, entry-now countdown, strength, measured accuracy vs break-even,
active factors) and a distinct sound plays: rising chime = BUY, falling = SELL, softer = tier B, then a win/loss cue when it settles.
If the Quotex tab is not in front you also get a desktop notification (click it to jump back). Settings and a **Send test alert** button are in the popup.
After updating, reload the extension (accept the new *notifications* / *offscreen* permissions) and hard-reload the Quotex tab.

## Quotex Signal page — http://127.0.0.1:8787/admin/live
The operator console: master **Alerts ON/OFF** switch, **Pause all / Resume all** (restores every strategy's previous mode), **Presets** (built-in Standard / Observe / Off
plus your own saved setups), and a grid of every strategy with an Off / Paper / Live selector - tick several and apply a mode to all at once. Below it: pair picker,
live candlestick chart with candle countdown, and the **signal board** showing what every running strategy says on the selected pair right now. The original single-page
dashboard is still available at `/` (button "Classic view"). The strategy grid is a collapsible section (collapsed by default, remembered per browser).

## Strategy builder — http://127.0.0.1:8787/admin/strategies/new

A chart sits at the top of the builder and draws your candles, every indicator you add (overlays on the price, oscillators in panes below) and
▲ CALL / ▼ PUT markers where the whole strategy would have signalled. Conditions are built as sentences ("RSI(14) · is below · 30") from chips you
drag out of the Toolbox (or dropdowns, or a one-click Quick recipe); hover or click the 👁 next to any condition to shade the candles where it is
true. "Edit as text" still gives the raw expression language, and conditions the sentence form cannot express are kept as "custom" clauses.
Markers use your condition factors and gates only; built-in factors and filters are applied by "Evaluate now".

**Filters** veto a signal (ADX, volatility, hours, trend alignment, payout, one direction only, ...). **one per run** keeps only the *first* signal of a
back-to-back run (a signal is skipped when the same direction already signalled in the previous `gap` candles, 1-5): fewer repeated, correlated trades, same win
rate on the ones it keeps. Backtest and live use the same rule (`backend/tests/test_one_per_run.py` checks them candle by candle). Add it last in the filter list.

**Supply/demand zones** (indicator `zones`, `backend/app/zones.py`): finds zones the way you draw them - a tight base followed by a strong departure (up = demand,
down = supply) - and follows them: each separate visit is counted (fresh zones are strong, a 3rd visit is weak), a zone broken by a close through it flips role
(broken demand becomes supply on the same band and the reverse), and `room_up` / `room_dn` measure the ATRs to the next opposing zone. Fields: `dz_*` / `sz_*`
(lo, hi, tests, age, flip, since, move) for the zone just touched, plus the two room fields. `examples/supply-demand-zones.json` uses it: with the trend, at a
fresh strong zone with room to run, after a confirmation candle. A zone depends only on the candles since its own birth, so live evaluation (which a strategy with
this indicator gets 488 candles for) and a backtest give identical answers (checked on 11,587 real candles). Tests: `tests/test_zones.py`, `tests/test_zone_strategy.py`.

**Candle patterns** (factor kind "candle pattern"): a row of candle steps, oldest first, ending on the candle that just closed - e.g. 3-6 green candles
with higher highs, a green hammer whose low is below the previous low, then 1-3 red candles trading below the hammer's low. Each step has a colour,
a shape (hammer, shooting star, doji, strong/weak/long body), a repeat range and price rules against the previous candle or an earlier step. The
BUY and SELL sides are mirror images (one click copies and flips one into the other). Ready-made patterns are in the Toolbox. On the chart each
step's candles are boxed and numbered. Patterns run in live signals, backtests and the chart through the same matcher (`backend/app/patterns.py`).

## Trade generator — http://127.0.0.1:8787/admin/generate
Pick a pair (OTC / Live), an expiry (1m / 5m / 15m), your time zone and either "next candle" or a specific time, choose which strategies take part
(running / all / hand-picked) and a minimum grade, then **Generate trade**. Every chosen strategy analyses the last closed candles; the answer is one trade idea
(CALL / PUT, grade A-C, entry and expiry time, the reasons, a check of the other two timeframes) or an honest **NO TRADE** (disagreement, feed stale, data gap,
too few candles). The table "Does agreement actually help?" shows measured accuracy by number of agreeing strategies, so you see evidence rather than a promise.
"Conviction" is agreement strength, never a win probability. A time in the past replays what the app would have said and shows the real result. Generated CALL/PUT
trades are saved, settled automatically (next candle open -> close) and summarised as the generator's own track record. Code: `backend/app/generator.py`,
test: `backend/tests/test_generator.py` (takes ~1 minute, builds a synthetic session).

## Admin panel (React) — http://127.0.0.1:8787/admin/
When signals stop, a "Signals are paused" banner (side panel and Live page; `health` in `/api/state`, `Engine.feed_health`) names the cause - no data, a hidden Quotex tab, a gap in the pair's candles with how many uninterrupted candles are still needed - and what to do (reload the Quotex page while it is visible, keep the window visible). Every strategy row in the side panel and on the Live page has a **readiness bar** (`/api/readiness`, `backend/app/readiness.py`, refreshed every 2 s): how much of the strategy's rule holds on the candle that is still forming, as if it closed now (3 of 5 conditions = 60 %, with the missing conditions listed) - grey far, blue building, amber near, orange almost, green / red READY (a signal would be issued if the candle closed as it is), purple blocked (a filter such as the payout refuses it). It is a reading of the market's state, not a chance of winning, and the header names the closest live strategy even while the group is collapsed. The side panel lists the LIVE strategies' signals first, and its Live and Paper strategy groups both start collapsed. Overview, Signal history (every column heading sorts the WHOLE filtered list on the server - click: natural direction, again: reverse, again: back to newest first; the pair filter is a searchable multi-select of every available pair with its signal count (`/api/signal-pairs`, `symbol=A,B` on `/api/signals`); **MTG-1 / MTG-2 columns** show what each settled signal came to with a one- or two-step martingale (win / ✓ M1 / ✓ M2 / ✗ lost / skipped while a ladder ran) and a strip above the table gives flat vs MTG-1 vs MTG-2 accuracy AND net units over the whole filter; with per-signal inspector, notes/tags, similar signals), Strategies (visual builder + JSON, lifecycle, versions; a strategy's page shows its accuracy plain, with a one-step and with a two-step martingale - overall, by timeframe and by tier - each with the net units it really made; below that, the strategy's own full Signal history - the same sortable, filterable table with the MTG columns and the signal inspector), Backtest lab,
Clinic (loss analysis + "try this filter"), Sweeps, Research (nightly next-candle check), Data (collection plan, coverage, gaps, CSV export, instruments), Alerts, System.
The **Collection plan** tab on Data says which well-paying pairs to open on Quotex and how far to scroll each chart back, with progress toward a data target
(default 100,000 1m candles on pairs paying 80 %+; live capture alone adds only 60 candles per hour per open pair, scrolling back loads days at once). Test: `tests/test_plan.py`.
The **Sentiment** tab shows which pairs report trader sentiment (Quotex only sends it for pairs its page follows; the extension is read-only and cannot ask for more),
stores a reading per pair every 20 s, and tests live whether the crowd predicts the next candle (only readings known *before* the candle opened; an edge needs
>= 1,100 candles per range, |z| >= 3 and the same direction in both halves of the data). Code: `backend/app/sentiment.py`, test: `tests/test_sentiment.py`.
The **Strategies** table sorts by any column title (click again to reverse; "Back to default order" resets): the default is live strategies first, then highest
accuracy. **MTG-1 acc.** is each strategy's win rate on its own real settled signals if every loss got one re-entry on the next candle, with the net result under it
(computed in the background and cached 20 s; `backend/app/mtg.py` `signals_summary`, test `tests/test_strategy_mtg.py`).
Every run in the lab's Runs table also shows **With MTG-1** (win rate if each losing trade gets one re-entry on the next candle, stake x2.2, with the net result under it)
and **Won by MTG-1** (how many trades the re-entry won); older runs are filled in automatically in the background. A one-step MTG always lifts the win rate (a 50 %
strategy reads 75 %) while a lost ladder costs 3.2 units, so judge it by the net figure, not the percentage.
The Backtest lab draws one zoomable, scrollable candlestick chart per selected pair (wheel = zoom, drag = move, overview strip, trade-to-trade
jump) with the strategy's BUY/SELL signals and each trade's win/loss; **MTG** (martingale: off / 1-3 steps, stake multiple, default 2 steps x2.2) boxes the
re-entry candles after a losing trade (M1 / M2 with a win/loss mark) and a panel shows what the ladder really did - rescue rate, ladders lost, net result vs flat,
worst ladder, deepest drawdown, biggest stake; a signal that fires while a ladder is running cannot be taken and is left out (`backend/app/mtg.py`, `tests/test_mtg.py`); the same charts appear on a finished run's page with its validation period shaded.
**Market structure** (`backend/app/structure.py`, indicator type `structure`, `tests/test_structure.py`): swing highs/lows -> `ms.trend` = +1 while the market makes higher highs and higher lows, -1 after a lower high followed by a break of the last higher low (or lower lows), 0 when unclear; `examples/structure-zones.json` trades demand zones only in an up-trend and supply zones only in a down-trend, strong fresh zones only. `tools/bt_compare.py` backtests spec files read-only.
On any chart, a strategy that uses the `zones` indicator draws every supply zone **red** and demand zone **green** as a rectangle (fresh = solid, broken or flipped = dashed, hidden unless "Broken" is ticked), outlines the **BASE** candles that formed it (dashed) and the **DEPARTURE** candle (solid), puts a diamond where price came back to it, and hover tells which candle is which; a strategy with the `structure` indicator labels every swing HH / HL (green) and LH / LL (red). These are also built-in chart features: the Live chart and the strategy builder draw zones and structure with default settings even when no strategy (or a strategy without those indicators) is applied, each with its own checkbox (`marks: true` on `/api/strategies/chart`). Toggles are in the chart toolbar (`zones_mod.lifecycle`, `structure.pivots`, `chartdata._zone_and_swing_marks`).
`examples/zb-*.json` (written by `tools/make_zone_breakout_specs.py`) are the zone **reaction**, **breakout** and **flip-retest** set-ups, alone and combined (`zb-all-in-one`); on the stored 1-minute history none of them beat break-even (about 48-51 % against 52 %), so run them in paper mode only. `examples/tp-*.json` (`tools/make_trend_pullback_specs.py`) trade WITH the structure after a retracement; `tp-diagnostic-follow` signals every candle of a confirmed structure trend and measured 50.1 % over 43,771 one-minute candles (and 50.2 % on 5m): the structure trend alone says nothing about the next candle, and the pullback variants stayed at 50-51 % against a 51.8 % break-even. The `zones` indicator also measures zone **strength from the candles** (`tight` base / ATR, `dep` departure body ratio, `run` how far price travelled away, in ATRs): this OTC feed has no usable volume (about 80 ticks on every candle, correlation with the candle's range about 0.03). `examples/zs0..zs4-*.json` (`tools/make_zone_strength_specs.py`) are the same zone reaction at rising strength; accuracy did not rise with strength (50.9 / 47.7 / 51.9 / 55.8 on 78 trades / 50.0 on 6 trades, break-even 52.1 %). `examples/cf1..cf3-*.json` (`tools/make_confluence_specs.py`) require the Heikin-Ashi Continuation and MACD Histogram Cross signals to agree (same candle / MACD flip within 3 candles / MACD on the right side of zero): 49.7-50.0 % over 4,000-12,000 trades against a 52.8 % break-even, no better than either signal alone (50.1 % / 49.8 %) - two indicators built from the same price momentum do not confirm each other. `tools/signal_features_study.py <spec> --tf 60` asks whether anything visible BEFORE a signal (buying / selling pressure, close location, an over-extended move, RSI stretch, streaks ...) separates its winners from its losers, fitted on the older 70 % and re-checked on the newest 30 %; for the engulfing-candle zone strategy (8,817 trades, 49.4 % wins) none of twelve such features held up (correlations under 0.04, flipping sign on the newer data). Also tested on the same strategy and found to carry nothing: trader sentiment (crowd on the signal's side: 45.2 % for wins and for losses; over 5,800 candles the crowd's % up vs the next candle was 48-52 % in every range), waiting one more candle before signalling (49.1 %), and the candle's body / wick shape (a -0.26 correlation seen on 114 live signals was +0.02 on 8,817 historical trades). The strategy page has an "Is it proven yet?" card: track record vs break-even, how far it is from a provable verdict (about 1,100 settled signals for a 3-point edge), and a warning when a live strategy has not shown an edge. A one-rule strategy's "strength" is always 100 and is not shown as such any more: the signal views show the strategy's measured track record instead. `tools/bt_compare.py <spec files> --mtg 1` backtests spec files read-only, flat and with a martingale.
**Engulfing-candle zones** (`backend/app/engulf.py`, indicator type `engulf`, `tests/test_engulf.py`) are the chart's default zones: a red candle engulfed by a green candle (or a run of up to 3) is a DEMAND zone, its full high-low range; a green candle engulfed by red is a SUPPLY zone. Zones are marked wherever that happens, in any trend; the market structure decides whether a strategy trades them (`ms.bias`: an up-trend lasts while the last higher low holds, a down-trend while the last lower high holds, the newest swing decides). A zone works for ONE visit: every candle while price is inside it can confirm (a pullback candle touches, the strong candle after it confirms), and it is used up when price leaves; a close through it kills it. `examples/ez1..ez4-*.json` (`tools/make_engulf_zone_specs.py`) trade the confirming candle with the structure (about 15 trades per pair-day for ez1): on the stored 1m history 49.9-51.0 % against a 52 % break-even, i.e. no edge - paper only. The older base/departure zone indicator (`zones`) is still there for strategies that use it.
**One chart everywhere**: every chart in the admin panel (Backtest lab, a run's page, Live signal, the strategy builder, the signal drawer) is the same component,
`admin/src/components/chart/PriceChart.tsx` (zoom +/- and mouse wheel, drag or ◀ ▶ to scroll, 50/100/250/500/All, Latest, trade-to-trade jump, overview strip,
crosshair tooltip, BUY/SELL and result toggles, **full screen** with the button or key `F`, `Esc` to leave). `SmartChart.tsx` wraps it for any screen that only has a
pair and a timeframe: it loads the history, follows the live candle, lets you apply **any strategy** (its trades, win/loss, MTG and indicators incl. supply/demand zones).
Indicators, zones and structure are drawn over every loaded candle: the server cuts the history at data gaps and works out each uninterrupted stretch (30+ candles) on its own, so nothing spans a gap and older candles are no longer blank (`chartdata.build_all`, `Engine.chart_rows_all`). The strategy builder still draws its newest 400 candles.
**Research** is a nightly check (03:00 UTC by default; set `QXS_RESEARCH_HOUR=0-23` or `off` before starting the backend; a missed run is made up when the backend
starts) that asks whether a model - logistic regression and gradient boosting, plain numpy, nothing to install - can predict whether the NEXT 1m candle closes up from the
last 5 or 10 closed candles, scored on the newest 30 % of the data it never saw. It reports AUC against the chance band for the sample size, a shuffled-label self-check
and verdicts no_signal / weak / signal / need_data / control_failed; a result only counts when it is significant after correcting for the models tried, at least 0.52,
and on >= 5,000 unseen candles. "Run now" is on the page. Code: `backend/app/research.py`, `backend/app/minigbm.py`, test: `backend/tests/test_research.py`.

**Sweeps** scores many strategies at once the strict way: one shared time cut (the newest 30 % of the data is a holdout nothing is tuned on), the
bar is the break-even win rate of each pair's payout (not 50 %), and the holdout p-value is multiplied by the number of candidates *ever* swept, so
trying more ideas raises the bar instead of manufacturing a "winner". Verdicts: PASS / PROMISING / OVERFIT / NEED DATA / NO EDGE. A pass is evidence
to start paper-trading, never a promise. Also available as `.venv\Scripts\python tools\sweep.py --all` and, with parameter grids
(`{"grid": {"gates.min_agree": [2, 3]}}`), via `POST /api/sweeps` (see `tools/sweep_example.json`). Code: `backend/app/sweep.py`, test: `backend/tests/test_sweep.py`.
It is built into `backend/static/admin` and served by the backend. To change it:
```
cd admin
npm install        # first time
npm run dev        # hot-reload dev server on :5173 (proxies /api to :8787)
npm run build      # type-check + build into ../backend/static/admin
npm test           # unit tests of the strategy form model
```
Note: `start.ps1` runs uvicorn with `--reload`, so saving any backend `.py` file restarts it; a syntax/import error in that file takes the backend down until fixed.

## AI advisor — http://127.0.0.1:8787/admin/ai
An open, dependency-free model (`app/ai.py`, `app/minigbm.py`: gradient-boosted trees, no cloud, no API key) reads every closed 1-minute candle through ~56 candle-psychology features (wick rejection, close position in the range, body/range, engulfing, hammer/star, runs of colour, market structure, engulf zones, volatility) and estimates the chance the next candle closes up.
- **It must earn its say.** Training uses an expanding walk-forward (always tested on later candles than it learned from, with an embargo), plus a shuffled-label control that must sit at AUC 0.50. Only a verdict of *proven* (AUC clearly above the chance band in every fold) lets it confirm / veto signals; its **live record** (every call it makes on live candles is logged in `ai_log` and scored against the next candle) can switch it off again. Otherwise signals say "AI: no proven skill".
- **Learns from history and live data**: every night (same hour as Research) it retrains on everything stored, including candles collected live. Training runs in a separate low-priority process (`python -m app.ai`), so the live feed is never slowed. `Train now` is on the AI page; progress is in `data/ai/progress.json`.
- **Reliability map**: for hour / pair / volatility / structure / zone / last-candle situations it lists where its confident calls did better or worse on unseen data (Benjamini–Hochberg corrected, and the pattern must hold in both halves of the test period). An empty list is the normal, honest answer.
- Side panel card shows its reading for the selected pair; `/api/ai/status`, `/api/ai/read?symbol=&direction=`, `POST /api/ai/train`.
- Set `QXS_AI=off` to disable. **Result so far: AUC ≈ 0.50 on ~64,000 unseen candles — no proven skill, so it confirms nothing.** Candle direction on these OTC charts is close to a fair coin.

**Real-market candles for the AI (`app/marketdata.py`)**: the OTC pairs are priced by the broker and look like a fair coin, so the backend also pulls 1-minute candles of the 20 live-market forex pairs from a free public source (Yahoo Finance's chart endpoint, no account) and stores them as `<PAIR>_mkt` (e.g. `EURUSD_mkt`, `source='yahoo'`) beside the Quotex data - never mixed with it. About 28 days of history are fetched at first (~550,000 candles); after that a refresh runs at start-up and every 6 hours and only adds what is new. The AI advisor, AI Momentum, Edge Lab and research read them on their next run. `GET /api/data/market` shows the state, `POST /api/data/market/refresh` fetches now, `QXS_MARKETDATA=off` disables it. The prices are the interbank market's, not Quotex's own quote, and the source may change or stop; a failed refresh just reports the error. Closed live markets show a placeholder payout of 20 %, which is no longer allowed to keep a pair out of the AI's training. Test: `backend/tests/test_marketdata.py`.

**My style (`app/style.py`, admin page `/admin/style`)**: learns what your own trades have in common and tests whether it works, then runs the best habit live. Only first trades count as decisions (martingale steps and repeated clicks are forced by an earlier result). For each, the market is described as it was at your entry from the stored candles only (how far price had moved inside the candle in ATR, seconds into the candle, last candle colour, 5-candle return, EMA slope, RSI, Bollinger position, ADX, streak ...), and ~20 habits ("you bet against the candle's own move", "you enter in the first 5 seconds" ...) each get a win rate with a 95% range widened for the number of habits compared, against the break-even rate of your payouts: proven / promising / weak / against / too few. A habit that beats break-even in your own trades (8+ trades) becomes a live rule - today "fade the candle's move": when the forming candle has moved at least X ATR one way, N seconds in, signal the other way until the candle closes, with X and the time window taken from YOUR trades and pairs where your record is below break-even skipped. The rule runs on the live ticks, every signal is saved in `style_signals` and settled at the candle close (a win = the close is on your side of the entry price, like your own trades; a candle thrown away for missing ticks voids the signal), so it earns its own record. Alerts (same card and sound as signal alerts) stay off until it has 30+ settled signals at or above break-even (setting: earned | every signal | off). Said plainly on the page: 30 trades cannot prove a style; the live record is the real test. `GET /api/style`, `PUT /api/style/settings`. Tests: `backend/tests/test_style.py`.

**Trading guard (`app/guard.py`, admin page `/admin/guard`)**: a daily profit target, a daily loss limit (stop-loss), a losing-streak break, speed / daily trade limits, trade-size limits and an overtrading watch, all computed from the trades you really place (see My trades) and delivered like the signal alerts - a card on the Quotex page with a sound (target / heads-up / warning / stop tones) and a desktop notification when the tab is in the background (popup option "Trading guard alerts"). Read-only: it tells you, it never blocks or places a trade. Limits are an amount or a % of the balance you started the day with (balance now minus today's result); a one-step martingale cycle counts as ONE trade / ONE loss; clicks on the same pair, side and expiry are one position. Alerts fire once per day per event (`guard_alerts` table), things that already happened more than 3 minutes ago are recorded silently so switching it on never floods you, and a trade opened after the target, after the loss limit, during a break or after "I am done for today" is flagged as overtrading (a warning for the first `extra_allowed` trades past the target, then danger). The page shows today's status and a gauge between the loss limit and the target, a card per rule, a suggested stake for the next trade (risk share spread over the first trade and its martingale step, cut down near the loss limit or in a streak), your rules, the alert history, the last 14 days, and a status chip on every admin page. `GET /api/guard`, `PUT /api/guard/settings`, `POST /api/guard/stop-today|resume|test`. Tests: `backend/tests/test_guard.py`.

**My trades (`app/broker_trades.py`, admin page `/admin/trades`)**: the trades you place on Quotex and how they ended. The extension (still read-only) forwards the order messages your Quotex tab already receives - an order sent, opened, closed with its result - as `k:"o"` items carrying only a whitelist of trade fields (never balance, account or login data). The backend keeps one row per trade in `broker_trades` (stake, pair, side, prices, profit, win / loss / draw, real or demo) and the last 400 raw messages in `broker_events`. The page shows net profit, win rate against break-even, trades per day with a running total, per pair, per side, and whether each trade followed a Tradzen signal (same pair and direction shortly before entry), was your own call or went against the signal. `GET /api/trades?account=all|real|demo&days=N`, `GET /api/trades/raw`, `DELETE /api/trades/{id}` (removes a trade from the list: it is hidden, not erased, so it stays gone when Quotex resends it; the page offers Undo for 10 seconds, `POST /api/trades/{id}/restore`, and "Restore all" for removed ones, `POST /api/trades/restore`). Quotex also sends your recent closed trades when the tab loads, so today's earlier trades appear too. **Balance and currency:** the extension also forwards the account balance messages (live and demo balance and the currency - nothing else of them), shown in a bar on top of every admin page, where an eye button shows / hides every amount in the admin (hidden by default, remembered in the browser); every money value on My trades uses the account currency (₹ for INR, $ for USD, R$ for BRL ...) via `GET /api/account`. Other pages (backtests, strategies, signal history) are in units of the stake, not money. **Trade window:** click any trade (or martingale cycle) to open its details - the 1-minute candles around it with the second you entered and the second it expired shaded, the candle(s) it ran through outlined, entry and exit price lines, a profit / loss zone, the signal that was on screen, the position and martingale cycle it belongs to, and plain-English facts (price move, seconds into the candle, payout, return). `GET /api/trades/{id}/detail`. ← → browse trades, Esc closes. **Martingale, one step:** orders on the same pair, side and expiry count as one position (two clicks of 1 = one step of 2); a position on the same pair opened within 90 s after a loss closed is that loss's MTG step; a lost step ends the cycle. The page shows cycles, steps taken / recovered / lost, and your result with vs without the steps. Profit is read from Quotex's reported `profit` (net gain or whole return; a lost deal reports 0) - if a result ever looks wrong, the raw messages at the bottom of the page show what Quotex sent. Tests: `backend/tests/test_broker_trades.py`, `extension/test_hook.js`.

**Risk advisor — learn from the old backtest data (AI advisor page, bottom section)**: for a strategy it replays all stored candles (`app/risk.py`, separate low-priority process), takes every backtest trade with its entry context (RSI, ADX, volatility, Bollinger position, wicks, EMA trend, hour …) and learns *where it loses*:
- a **risk model** (P(win | context), walk-forward — always scored on later trades; its riskiest 25 % must win clearly less than the rest, in both halves of the unseen period, or it is "not used");
- **loss rules** (the Clinic's single-situation findings: significant after false-discovery correction *and* confirmed on the newest 30 % of trades).
Live signals that match a confirmed rule (or the risk model's riskiest group) get a **⚠ RISKY** tag with the reasons (side panel, Signal history, signal details). The confirmed rules are also added one at a time to a copy of the strategy; a filter stays only if the newest trades improve — the copy is created as a **new paper strategy** (button *Create as new paper strategy*), the original is never changed, so the improvement is measured live before anyone trusts it. API: `GET /api/risk`, `GET /api/risk/{id}`, `POST /api/risk/{id}/analyze`, `POST /api/risk/{id}/apply`.
Honest limit: it removes the worst *situations*; if a strategy has no edge to begin with, filtering rarely creates one. On the real data so far (Confluence 5-Factor 34,263 trades, Confidence 6 Factor 11,117 trades) it found no reliable loss pattern: their losses are indistinguishable from chance, so nothing is tagged.

**Automatic re-checks and upgrades (champion / challenger)**: every night (same hour as Research) every live and paper strategy is queued for a risk re-analysis, one at a time in the low-priority process (`QXS_RISK_NIGHTLY=off` disables). When a filter holds up on the newest backtest trades, a filtered copy starts as a **paper challenger** (`QXS_AUTO_UPGRADE=off` disables; at most 3 per day, one at a time per strategy, never the same filters twice). It is judged only on its real live signals: **promoted** to live (its parent paused) only when 300+ settled signals prove the win rate's 95 % lower bound is above break-even; **retired** (archived) when proven worse, no better than its parent over the same period, or still unproven after 1,000 signals. Nothing is ever promoted on backtest numbers alone. The log is on the AI advisor page (`GET /api/upgrades`).

**Model bake-off with modern libraries** (`tools/ml_bakeoff.py`, run with the separate `backend\.venv-ml` that holds LightGBM, scikit-learn and PyTorch - the live backend stays dependency-light): the app's own trees, logistic regression, tuned LightGBM and a CNN / GRU / Transformer on the raw last-32-candle window, all on the same walk-forward protocol with a shuffled-label control. A model is only adopted if it proves skill on unseen candles; results are in `data/ai/bakeoff.json`.

**Edge Lab (admin → Edge Lab)**: the AI's search for an edge, run by itself every week (and on demand) in a separate low-priority process (`app/edgelab.py`; `QXS_EDGELAB_WEEKLY=off` / `QXS_EDGELAB_AUTO=off` switch the weekly run / automatic creation off). Stage 1: a walk-forward model asks whether anything predicts the next candle at all (AUC + shuffled-label control). Stage 2: ~35 plain-language conditions (trend, momentum, candle shape, bands, volatility, session) are combined into thousands of 1–3-condition rules (follow or fade); the history is cut in time - DISCOVERY (oldest 50 %) ranks them, CONFIRMATION (next 20 %) must back the top 30 with a Bonferroni-corrected test, and only the survivors see the newest 30 %, through the same battery as `idea.ps1` (real backtest of the real strategy spec, the ledger widening the 95 % range for every idea tried). If nothing survives, the best rule is still built and tested, so the answer is concrete. Stage 3, only if a rule PASSES: it becomes a PAPER strategy, and every live / paper strategy is tested as a copy that must ALSO satisfy the rule - improved copies become paper challengers (judged on real signals like every upgrade). No edge → it says so and changes nothing (the "Install best rule on paper anyway" button only measures it live). API: `GET /api/edgelab`, `POST /api/edgelab/run`, `POST /api/edgelab/runs/{id}/apply`. The test battery lives in `app/battery.py`.

**One-command idea test** (`idea.ps1` → `backend\tools\idea_test.py`): `.\idea.ps1 expr --call "<cond>" --put "<cond>"` (or `spec file.json`, `model`, `ledger`, `ai-momentum` - replays the AI-built momentum strategy with its rules learned only from the older 70 % of candles) runs the same fixed battery on every idea in seconds: all pairs paying 85 %+, every timeframe, an older 70 % vs a newest 30 %, 5 time blocks, two pair halves. **PASS** needs ≥ 1,500 trades, the newest 30 % clearly above break-even (95 % range clear of it), the older 70 % above, ≥ 4 of 5 blocks above and both pair halves above; **PROMISING** = above on the newest data but unproven; otherwise **FAIL** with the gap in points. Every idea is written to a ledger (`backend\data\ideas\ledger.jsonl`, reports as JSON beside it) and the 95 % range is widened for the number of ideas tried in the last 90 days - the more you try, the more a lucky result is expected, so proof gets harder. `--install` creates a PAPER strategy only for PASS / PROMISING ideas. Exit code 1 means FAIL. The expression names (e9 e21 e50 a14 r14 ad mc bb st ms, candle names, patterns) are listed in `idea.ps1 expr -h`.

**AI builds the strategy (Trade generator → "✦ AI builds it")**: no predefined strategy. `app/momentum_ai.py` (1) finds the *initial point* of the current momentum (the newest confirmed swing low/high, no look-ahead) and measures the leg from there (age, ATR distance, efficiency, share of candles going with it, pullback depth, acceleration, ADX); (2) learns a small decision tree from the same measurements on every stored candle of every pair - labelled "did the next candle continue the leg?" - fitted on the older 70 %; (3) tests every rule on the newest 30 % (unseen candles) with a 95 % range widened for the number of rules; (4) the current momentum falls into one rule → follow / fade → the trade, graded by the rule's own test (A proven above break-even, B above but not proven, C no edge). The learning runs in a worker thread and is cached for 30 minutes. Trades are saved and settled like the other generated trades. Real data: every rule tests at about 50 % (next candle continues the leg 50.1 % of the time), so the AI honestly reports grade C - "no edge found" - and "B or better" returns NO TRADE.

**AI MOMENTUM as an automatic paper signal source**: the built-in strategy "AI MOMENTUM (auto - builds its own rule)" (`ai-momentum`, paper, 1m) records a signal on every closed candle of every streaming pair using the rule the AI learned (see above) - no preset spec is evaluated; `engine._run_strategies` asks `momentum_ai.auto_result`. It waits out data gaps, never blocks the candle handler while the model is (re)learning (a worker thread builds it; "warming up" skips meanwhile; refreshed every 30 min), and `QXS_AI_MIN_GRADE=B` (or A) records only situations whose own test beat break-even (none so far, so that setting means no signals). Its signals are settled and scored like every strategy, so the Strategy health card and Signal history show its real win rate against break-even - the honest answer to "does the AI strategy work?". It is not part of the nightly backtest queue.

**Confirmed, scalable strategy** (`tools/make_confirmed_specs.py` → `examples/cs1…cs3`): six independent readings (EMA stack, MACD, structure, close control, RSI momentum, +DI/-DI) must agree, none against; all pairs paying 85 %+, all timeframes (~150 signals per pair-day for `cs1`, installed as the paper strategy "CONFIRMED SCALE"). Study on 80,569 candles: win rate does **not** rise with the number of confirmations (1 vote 49.7 %, 8 unanimous trend votes 49.7 %, reversal votes 48.8 % at 3+) and the strict versions are worse on the newest data (cs2 47.7 %, cs3 47.0 % vs ~52.4 % break-even). Confirmations are not independent evidence on a near-random series, so stacking them cuts volume without raising accuracy.

**Trend regime, silent when sideways**: `tools/make_trend_regime_specs.py` writes `examples/tr1…tr4` (EMA9>21>50 + ADX ≥ 22 + fanned EMAs = trending → a signal on nearly every candle that follows the trend; the shift into a down-trend is its own rule; otherwise no signal). Backtested on ~22–23k trades (89 per pair-day): 49.9–50.1 % win vs ~53 % break-even, in every variant. `tr4` is installed as the paper strategy "TREND REGIME (silent when sideways)".

**Candle-psychology signal on every candle**: `tools/make_candle_psychology_specs.py` writes `examples/cp1…cp3` (rejection wicks, engulfing, close control, exhaustion after a run, last-colour fallback). Backtested on ~68,000 candles: 49.9–50.2 % win vs ~53.4 % break-even — it produces a signal on every candle, but not a profitable one.

## Privacy
The extension forwards prices, candle history, instrument list/payouts and trader sentiment only. Auth, session, balance, orders and account fields are never forwarded.
The backend listens on 127.0.0.1 only.

**One-step martingale on the rule's record** (My style page): when a signal of the live rule loses, the page also plays one martingale step on paper: the same side again on the next candle, entered at the losing candle's close, with 2x the stake. The record shows how many steps won, a "One step" result per lost signal, and the profit in units of the first stake, flat versus with the step. Signals recorded before this existed are filled in from the stored candles. It is only a measurement: a step wins only as often as the market lets it, and it cannot create an edge.

## Hosting for other people (accounts and roles) - phase 1

By default nothing changes: on your own machine sign-in is **off** and every request must come from the machine itself (a request with an `X-Forwarded-For` header is refused, so a dev server can never be exposed behind a proxy by accident).

Set `QXS_ENV=production` (or `QXS_AUTH=on`) to host it. Then sign-in is required for everything:

- `QXS_SECRET_KEY` (16+ random characters), `QXS_ADMIN_USER` and `QXS_ADMIN_PASSWORD` (10+ characters) are required. The admin is created/updated from them at every start and can only be changed in `.env`.
- Every other account is created by an admin on the **Users** page (no public sign-up). Roles: **Admin** (everything), **Editor** (strategies, backtests, signals, data; no users/system), **Trader** (their own account page; more features arrive with the Features section).
- Every API route is closed unless listed in `backend/app/auth.py` (`_RULES`); a route nobody has classified is admin-only. Passwords use scrypt; sessions are HttpOnly/Secure/SameSite cookies that an admin can revoke; five wrong passwords lock a sign-in for 5 minutes; admin actions are in an audit log.
- The extension signs in from its popup (**Connection**: username + password, which gives that browser its own revocable token) or uses a personal **access token** (My account -> Chrome extension); https only. The extension reads the Quotex account number from the account's own order / balance messages, sends only a SHA-256 of it, and the server ties the first one it sees to that Tradzen account (`QXS_QUOTEX_LINK=on`, default; only a keyed hash is stored). Trades, balance and alerts of any other Quotex account are refused until an admin unlinks (Users page). It stops accidental mixing and account sharing; it cannot prove ownership of a Quotex account (Quotex offers no way to). Only a token marked *price feed*, which only an admin can create, feeds the shared market; other tokens only receive alerts.
- **Shared candles** (`backend/app/contrib.py`, `QXS_CONTRIB=on`): besides the price feed, every signed-in extension offers the chart history its Quotex page loads (`h` items) to the one candle store. First write wins: the server only inserts candles it does not have (tagged `contrib:<account id>`), never changes a stored one, and records disagreements for the admin. Candles are validated (closed, aligned, sane OHLC, no jumps, price level near the stored ones), accounts and the whole server have write allowances (an over-limit batch gets "busy, retry in N s" and is not queued), accounts whose candles are mostly refused are paused (the admin can also pause, resume or remove an account's candles under Data → Shared candles). A contribution that closes a hole in a streaming pair is used by the engine at once, and the extension shows the ranges the server wants. Live ticks still come only from the price feed.
- **Live prices from ordinary accounts** (`backend/app/leases.py`, `QXS_LIVE_FEED=on`): any signed-in extension may stream the live ticks of the pairs open in its Quotex tab, but **one account holds each pair at a time** (a lease). The extension reports which pairs it sees (`tp`) and the server answers which ones to send (`feed.send`: held pairs, free pairs, short spot-checks on held ones); other accounts' ticks are only compared with the held ones. The admin's price-feed tab always has priority; a silent holder loses the pair after 5 s. Ticks are checked (age, order, 2 % jump, level against the stored candles), rate-limited per account and server-wide, and an account that is mostly refused or disagrees with the others is paused automatically. Candles built from an account's ticks are tagged `tick:<account id>` so the admin can remove them (Data -> Live feed). Tests: `backend/tests/test_leases.py`, `extension/test_background.js`.
- Still to come (see the plan): the Features/plans section, per-user trades/guard/style, strategy publishing and the Docker + Caddy deployment files.

**Features and plans (phase 2).** The admin's **Features** page lists every menu and capability (`backend/app/feature_flags.py`) with one column per **plan** (a named set of switches and limits; seeded with "Standard", the default). On the **Users** page each user gets a plan, an optional end date (afterwards they fall back to the default plan) and per-feature overrides. A user gets: admin = everything; otherwise the role must be high enough (a plan can never give a Trader a staff feature), then the user's override, then the plan, then the feature's default. The server enforces it on every request: a menu's API returns 403 when the feature is off, "Connect the Chrome extension" gates token creation, and "Receive the admin's signals" gates the alert events. Features marked "not active yet" (personal trading pages, strategy publishing, per-user limits) are stored now and start working when the data is per-user and strategies can be published.

**Private data per user (phase 3).** Everything that belongs to one person - their broker trades and raw order events, trading-guard memory, learned style, settings, balance - lives in a database file of their own (`data/users/<id>.db`; deleting the user deletes the file). Nothing is filtered by a `user_id`, there is simply nothing shared, so one user can never read another's rows. The main database keeps the shared market (candles, instruments, signals, strategies) and the data that existed before accounts, which belongs to the admin from the `.env` file. Only a price-feed token feeds the market; every account's extension sends just its own orders and balance (the server answers `feeder: false` and the extension then stops sending prices) and polls for alerts about every 1.5 s. Private alerts (guard, the learned style rule) carry a recipient and reach only their owner; the shared signal alerts reach every user whose plan has "Receive the admin's signals". Traders now have My trades, Trading guard and My style (each behind its feature switch); the plan switch "Record own trades" decides whether their orders are stored. For other users, only signals that were really alerted (live) are matched with their trades.

**Strategy ownership and publishing (phase 4).** A strategy is either *shared* (made by an admin or editor) or a *user's own*. A user's own strategy is private: only they see it, change it, backtest it and receive its signals (it runs on the same shared candles; the plan limits how many they may keep and how many backtests they may run). A shared strategy has an **audience** that staff set on the Strategies page: **Testing** (staff only, the default), **Library** (published: listed in the Strategy library, a user adds it to receive its signals) and **Everybody** (every user receives it and may switch it off for themselves). The library shows a strategy's measured record, never its logic (its spec, the reasons behind each signal and its versions stay hidden from users who only receive it). Alerts are grouped within one audience only, so a strategy under test never appears inside an alert that users get. Signal history, stats and equity are limited to the strategies the caller owns or receives, backtest runs belong to whoever started them (a server-wide cap of 3 running at once), and the admin's tools (bulk control, the risk advisor, sweeps, the trade generator) only ever touch the shared strategies. Deleting a user removes their strategies, subscriptions and backtests.

**Hosting on a VPS (phase 5).** `DEPLOY.md` has the step-by-step guide. The pieces: `Dockerfile` (the admin is built in a Node stage; the backend runs on slim Python as an unprivileged user, one worker), `docker-compose.yml` (the backend, reachable only from the proxy, and Caddy with automatic HTTPS), `deploy/Caddyfile`, `.env.example` and `deploy/prepare.sh` (writes a `.env` with a random secret and admin password), and `deploy/package_extension.py` (builds the extension zip for your domain). In hosted mode the server adds browser-hardening headers (CSP, no framing, no sniffing), limits request size and the request rate of ordinary accounts, answers `/healthz` for the container health check, takes the real client address from the proxy for the sign-in lock-out, and makes a nightly backup of every database (`QXS_BACKUP`, `QXS_BACKUP_HOUR`, `QXS_BACKUP_KEEP`; admin API `GET /api/system/backups`, `POST /api/system/backup`). The Docker files were written without a Docker engine on the development machine: try them on a throwaway server first.

**Backups button and moving your data (follow-up to phase 5).** The System page has a Backups card (the nightly schedule, the list of backups with size and age, and a *Back up now* button). `python -m app.seed make` packs the database (a consistent snapshot, the server may keep running) and the AI / Edge Lab files into `seed/tradzen-seed.tar.gz`; on the first start of a new server the compose file's `QXS_SEED` loads it as the database, so the server starts with all the candles, history, strategies and trades. `python -m app.seed merge <seed>` later adds only market data (candles, sentiment, instruments) to a running server without touching accounts, strategies or signals. See DEPLOY.md, step 2b.

**Landing page and importing data from the admin (follow-up).** In hosted mode `/` shows a public marketing page (`backend/static/landing/index.html`, no scripts, honest about risk) to visitors who are not signed in; signed-in users go straight to `/admin`. `QXS_CONTACT` (a `mailto:` or `https://` link) turns on its "Request access" buttons. The System page has an *Import data* card: upload the file made by `python -m app.seed make`, then either add its candles to the server or, while nobody but the admin has an account, load everything and restart (the old database is kept beside it). `COOLIFY.md` is the walk-through for deploying with Coolify.
